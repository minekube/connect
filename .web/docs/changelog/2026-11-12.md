## October 8, 2026

- <VPBadge type='tip'>Gate</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **A Gate endpoint accepts Bedrock players without any identity configuration.** Connect issues a signed Bedrock identity, but Gate only advertised the explicitly configured v2 consumer, so an unlinked Bedrock player joining through Gate failed with `capability_unavailable` - including on v0.74.28, which read as a Connect problem rather than a missing Gate capability. [v0.74.29](https://github.com/minekube/gate/releases/tag/v0.74.29) enables a v1 consumer automatically for the official authenticated Minekube Watch service: it advertises `bedrock-identity-v1`, lazily fetches the current and previous verifier keys from the fixed HTTPS authority, and verifies the signature, endpoint/organization/session binding, expiry, canonical XUID and profile identity, and replay before it opens a tunnel. Reserved metadata is stripped from the profile the backend sees. No identity keys, URLs or capability settings are required, and the exceptions keep their own trust boundaries: custom Watch services, pass-through-only connectors and an explicit v2 require-mode are untouched, and an ordinary Java proposal never fetches Bedrock keys.

## October 13, 2026

- <VPBadge type='tip'>Gate</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **A Minecraft 26.3 backend can no longer disconnect its operators when the command tree arrives.** Minecraft 26.3 inserted five Brigadier argument types and moved two others, and Gate still resolved 26.3 ids with the 1.21.6 table. Every command tree that carried ids 57-61 failed to decode with `identifier not found`, Gate logged `backend server sent a packet that could not be decoded, closing connection` and the player saw `Internal server connection error` - and ids 55 and 56 decoded under the wrong names. Only operators receive a command tree, so only they were affected. [v0.74.40](https://github.com/minekube/gate/releases/tag/v0.74.40) maps the 26.3 table.

## October 17, 2026

- <VPBadge type='tip'>GeyserLite</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **A Bedrock client that stops answering no longer starves the Java backend's keepalive.** GeyserLite booted its embedded Geyser with `gameplay.forward-player-ping: true`, so Geyser answered the Java backend's `ServerboundKeepAlive`/`Ping` only when the Bedrock client echoed its `NetworkStackLatency`. A backgrounded or throttled mobile client, or a lossy UDP leg between the player and the edge, therefore left the backend's keepalive unanswered and Paper/vanilla dropped a healthy session with `Timed out` about 30 seconds after the first unanswered keepalive. Upstream Geyser's own default for this setting is `false` (MCPL answers keepalives itself); GeyserLite's baseline template and compose example had drifted to `true` and now match upstream. Reproduced with a real Xbox-authenticated Bedrock client against Paper 26.3, same client binary, only the echo behaviour changed. Install [v0.6.1](https://github.com/minekube/geyserlite/releases/tag/v0.6.1).

## October 18, 2026

- <VPBadge type='tip'>Gate</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **A MOTD containing an emoji no longer kills a 26.3 join.** Gate rebuilds the `minecraft:server_data` packet from the endpoint's ping MOTD, and an NBT string has to be encoded as Java's modified UTF-8 to carry a character outside the BMP - an emoji, astral CJK or a musical symbol. The client decoded it as `DecoderException: Failed to decode packet 'clientbound/minecraft:server_data'` about 0.8 seconds after spawn and closed the connection, while the edge logged nothing at all (the client closed), which is why this first read as a proxy/version mismatch. Only MOTDs with such a character were affected, which is exactly the "some 26.3 joins survive, some don't" shape reported on the fleet. [v0.74.44](https://github.com/minekube/gate/releases/tag/v0.74.44) encodes NBT strings as modified UTF-8.
- <VPBadge type='tip'>Gate</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **That rebuilt MOTD keeps its hover text, click action and shadow colour on 1.21.5+ clients.** The styling half of the same packet, not a second decode failure: the component holder was built without a protocol, so it selected the pre-1.16 JSON codec and a current client received `clickEvent`/`hoverEvent.contents` keys it no longer reads. [v0.74.45](https://github.com/minekube/gate/releases/tag/v0.74.45) encodes the MOTD for the player's protocol.

## October 21, 2026

- <VPBadge type='tip'>GeyserLite</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **Managed Bedrock no longer closes every join in the same second when HAProxy protocol is on.** GeyserLite rendered the Java-side HAProxy toggle at `java.use-proxy-protocol` under `config-version: 4`, while Geyser 2.x reads that switch only from `advanced.java.use-haproxy-protocol` and its v5 migration rewrites exactly one legacy path, `remote.use-proxy-protocol`. A key at the old path is in no migration path, so Geyser dropped it silently and never sent the header - and Gate's Geyser listener wraps each accepted connection in a requirement that the header be present, so the first read of the plain handshake died with `proxy protocol signature not present` and no Bedrock join completed. [v0.6.4](https://github.com/minekube/geyserlite/releases/tag/v0.6.4) renders the final path and drops the dead key from the baseline config.
- <VPBadge type='tip'>Connect plugin</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **A connector config option that cannot act now says so at startup.** `login-reassert.restore-full-profile` is read only inside the late pre-login and game-profile handlers, and every one of them returns early while `login-reassert.enabled` is `false` - so `enabled: false` together with `restore-full-profile: true` was inert with no warning, no error and no log line naming the keys. The field case (2026-10-21, endpoint `servermc4321`, Velocity with VeloAuth through a Connect tunnel) showed the offline UUID at the proxy while a direct join produced the Mojang UUID; the backend flagged the player as non-Mojang and the join died at the auth/limbo stage, and neither side's log said the option could not act. [0.15.17](https://github.com/minekube/connect-java/releases/tag/0.15.17) writes one startup warning for that combination.

## October 26, 2026

- <VPBadge type='tip'>GeyserLite</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **Native NetherNet ingress, and Bedrock 26.60 clients are accepted again.** v0.6.7 shipped NetherNet code that aborted at native startup because the bundled `libdatachannel-java.so` was omitted. [v0.7.0](https://github.com/minekube/geyserlite/releases/tag/v0.7.0) keeps the platform resources and the captured JNI callbacks, switches both Linux architectures to a dynamic glibc executable so the library can load, and verifies each Linux native image with HTTP discovery plus a signed WebRTC `NetworkSettings` round trip and a RakNet status answer. Fly needs different TCP and UDP binds: `GEYSER_SIGNALING_ADDRESS` works for the embedded and the subprocess runtime, `geyserSignalingAddress` overrides it for subprocess hosts, and UDP stays on the configured address; the example and troubleshooting pages describe the split and the advertised service IPv4. Bedrock 26.60 was carried in this release as an explicit preview backport of upstream's exact commit, and v0.7.1 replaced it with upstream stable 26.60 and dropped the preview patches, so install [v0.7.6](https://github.com/minekube/geyserlite/releases/tag/v0.7.6) rather than the preview.
- <VPBadge type='tip'>Gate</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **A Bedrock player can keep the collision-free leading dot in their name.** Gate rewrote a configured `.Steve` to `_Steve`, so an operator whose backend accepts the dot prefix (Paper does; vanilla does not) could not keep the Floodgate-compatible form. [v0.75.0](https://github.com/minekube/gate/releases/tag/v0.75.0) adds `bedrock.preserveDotPrefix: true` as a narrow opt-in and leaves the default unchanged. It preserves exactly one leading dot: spaces, interior dots and non-ASCII characters still become underscores, names stay capped at 16 bytes, and empty or dot-only names keep the `_` fallback. UUID selection and identity trust are untouched.

## October 28, 2026

- <VPBadge type='tip'>Connect plugin</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **A login Paper already refused is no longer driven further, and `debug: true` records both directions.** The post-1.20.4 fake login cycle called `callPlayerPreLoginEvents` and then `startClientVerification` unconditionally, even when Paper had already ended the connection inside the first call - a refused `AsyncPlayerPreLoginEvent`, or a velocity-forwarding refusal. Verifying a connection Paper has closed is a race whose result is either a no-op or a `LoginSuccess` written onto a refused login, contradicting the reason the player is being kicked for. The same release fixes a one-sided debug dump on Paper 26.3: 25 `Player -> Spigot` lines and zero `Spigot -> Player`, which read as "the backend sent nothing" for three support rounds, because Paper names the outbound encoder `outbound_config` on the injected configuration-capable connection and only uses `encoder` on the player-side path. [0.15.18](https://github.com/minekube/connect-java/releases/tag/0.15.18) stops driving Paper's verification after a login-phase refusal and captures both debug directions.

## October 29, 2026

- <VPBadge type='tip'>Gate</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **The 257th Bedrock session no longer stops Gate's managed Geyser.** Gate's managed Floodgate runner never read GeyserLite's bounded `ConnectionOpened` notifications, so the queue accumulated across the process lifetime and the 257th open stopped Geyser, disconnecting active Bedrock players; this was the defect behind the production rollback of the Bedrock 26.60 candidate on 28 October. [v0.75.10](https://github.com/minekube/gate/releases/tag/v0.75.10) drains only those transport notifications for that runner and cancels and joins the reader when the runtime stops. The regression fails on the old runner after exactly 256 opens with `verified ingress queue overflow` and the fixed runner processes 1,024.

## October 30 – 31, 2026

- <VPBadge type='tip'>GeyserLite</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **A converted Bedrock player is no longer kicked for flying while their placement cannot be proved.** GeyserLite's placement patch grounded a converted player only when it could prove a surface within 32 blocks and otherwise forwarded the client's own movement samples, so a client suspended in the air kept reporting `onGround=false` with nothing under it - a state a Java client cannot produce - and Paper's floating check (`clientIsFloating` plus `aboveGroundTickCount`, 81 ticks, about 4.05 seconds with `allow-flight=false`) disconnected it with `Flying is not enabled on this server`. Two gaps were closed: a placement whose real surface sits 33-384 blocks below was never grounded even while the session was being placed (customer control: feet `y=-18`, surface `y=-60`, 42 blocks), and there was no bounded bridge for terrain that genuinely cannot be proved. [v0.7.2](https://github.com/minekube/geyserlite/releases/tag/v0.7.2) resolves a pending placement against the world's own surface in the column and adds the bounded bridge; [v0.7.3](https://github.com/minekube/geyserlite/releases/tag/v0.7.3) holds on evidence instead of a 5-second timer, because a hold that kept re-sending the frozen position at an unsupported height re-armed the counter (measured on Paper 26.3-205: a 1 Hz position packet at `y=103` with the flag set was still disconnected about 4.7 seconds after teleport); and [v0.7.4](https://github.com/minekube/geyserlite/releases/tag/v0.7.4) holds by silence - while a placement cannot be proved against real terrain, no movement sample is forwarded at all. Install [v0.7.6](https://github.com/minekube/geyserlite/releases/tag/v0.7.6), which contains all of it.

## November 1, 2026

- <VPBadge type='tip'>GeyserLite</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **A suspended-placement hold now reports how and why it ended.** These holds are bounded, so knowing whether one was released by terrain, by a timeout or by the session ending is what separates a working hold from a player who was kicked anyway. [v0.7.5](https://github.com/minekube/geyserlite/releases/tag/v0.7.5) logs the end of the hold.

## November 3, 2026

- <VPBadge type='tip'>Gate</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **"Players may use `/server`, but `/send` stays restricted" now needs no Go extension.** Gate shipped no permission provider, so `requireBuiltinCommandPermissions: true` denied all three builtin commands to everyone: a player's permissions stayed undefined and `permission.Undefined.Bool()` is `false`. [v0.76.0](https://github.com/minekube/gate/releases/tag/v0.76.0) adds `config.permissions`, a file-backed provider Gate answers `proxy.PermissionsSetupEvent` with: `default` is granted to every player with no entry, a `players` entry replaces it, `deny` wins over both, patterns are exact nodes, trailing-wildcard prefixes (`gate.command.*` keeps the separating dot) or `*`, keys are UUIDs with usernames accepted case-insensitively as a convenience only (denials are a union over both forms, so a `players` UUID entry cannot bypass a username denial), an invalid key or pattern fails config validation instead of silently not matching, and a node the block does not mention stays undecided so another provider still decides it. The block is read when the proxy starts - a config reload does not re-register the provider yet - and only players are affected.
- <VPBadge type='tip'>GeyserLite</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **One session that runs out of memory no longer poisons every later NetherNet session.** On 2026-11-01 a long-lived ingress (v0.7.1, `-Xmx256m`) exhausted its heap inside `ZlibCompression.encode`; the `OutOfMemoryError` escaped the Netty run loop of both NetherNet player threads, Netty logged `Unexpected exception from an event executor:` once and terminated those executors permanently. The player event-loop group was created once per transport and every session was bound with `eventLoopGroup.next()`, so from that moment each new NetherNet session landed on a dead executor, `connectDownstream()` threw `RejectedExecutionException: event executor terminated` at `scheduleAtFixedRate`, `authenticate()` swallowed the throwable, and the client sat on "generating world" until its own timeout with its XUID still reserved - while the edge logged `Player connected with username <x>` after the throw, so the log claimed a login that never happened. [v0.7.6](https://github.com/minekube/geyserlite/releases/tag/v0.7.6) replaces a terminated thread group instead of handing it to new sessions.

## November 7, 2026

- <VPBadge type='tip'>Gate</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **A backend command tree Gate cannot decode no longer ends the session.** Gate parses `minecraft:commands` only to inject its own `/server`, `/glist` and `/send`, so a modded backend naming a Brigadier argument type outside the vanilla table made the tree undecodable and the decode error propagated out of the clientbound reader: Gate closed the connection about a second after placement, the player saw `Internal server connection error`, and the backend logged nothing. Measured on a Forge 1.20.1 backend (protocol 763, Forge 47.4.10) reached through the Connect edge; a tree whose layout desyncs the codecs part-way through reached it too, at a read offset that varied between attempts (8746 vs 8769 of a ~38 KB tree). [v0.76.3](https://github.com/minekube/gate/releases/tag/v0.76.3) keeps the raw body and forwards it byte-for-byte, so the session survives. A proxy hop does not need to understand a tree to forward it: proxy commands are not injected into that tree and `PlayerAvailableCommandsEvent` is not fired for it.

## November 9, 2026

- <VPBadge type='tip'>Gate</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **The server list can advertise your network's name instead of Gate's version range.** The advertised version string was built once at startup and the `status` block exposed only `showMaxPlayers`, `motd`, `favicon` and `logPingRequests`, so the only way to replace `Gate <range>` with a network name was a Go extension rewriting the ping. [v0.77.0](https://github.com/minekube/gate/releases/tag/v0.77.0) adds `status.versionName`. Empty (the default) keeps today's text exactly, and only the display string changes: the advertised `protocol` and the set of client versions Gate accepts are untouched, so a custom name never changes who can join.

## November 11, 2026

- <VPBadge type='tip'>Gate</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **A Forge or NeoForge backend's own status data survives Gate's server-list answer.** Gate models `version`, `players`, `description`, `favicon` and `modinfo` and dropped everything else when it re-encoded a status it had resolved from the backend, so a modded backend's `forgeData` (FML2/FML3), `neoforgeData` or any other provider-specific member vanished - a real Forge 1.20.1 backend's 376-byte status came back as a 136-byte vanilla one. [v0.77.1](https://github.com/minekube/gate/releases/tag/v0.77.1) keeps the members it does not model and merges them back verbatim; modelled members still win, so a stale value cannot shadow `version`, `players`, `description`, `favicon` or `modinfo`, and nothing is synthesized for a vanilla backend. Gate never interprets these values, and in Lite mode the ping is proxied unchanged and was never affected.
- <VPBadge type='tip'>Gate</VPBadge> <VPBadge type='warning'>Upgrade</VPBadge> **The message a player gets when a builtin command is refused is configurable.** `requireBuiltinCommandPermissions: true` answered a missing node with one fixed string, so a network that wanted to point at its own help channel had to fork it. [v0.78.0](https://github.com/minekube/gate/releases/tag/v0.78.0) adds `config.builtinCommandRefusedMessage` next to `requireBuiltinCommandPermissions`: `{node}` is replaced with the permission node the command requires (every occurrence, and a message without the token is sent as-is), and it takes the same `TextComponent` shape as `shutdownReason` and `motd`, legacy `§` colours or modern JSON. The default is unchanged and byte-identical - red `You don't have permission to use this command (requires "{node}").` - so nothing changes on an existing config.
